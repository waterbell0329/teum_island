## 프론트엔드 기술 아키텍처

### 폴더 구조

```
frontend/src/
  app/
    page.tsx              # 홈 (기본 진입점)
    onboarding/page.tsx
    letters/page.tsx
    quests/page.tsx
    closet/page.tsx         # 스트레치 기능, 지금은 빈 화면로 시작
  components/
    Character.tsx           # 3레이어 구조 (아래 참고)
    Fairy.tsx
    IslandBackground.tsx
    BottomNav.tsx
    InputFlow.tsx            # 자유텍스트/구조화 2경로
    FoodIcon.tsx
    LetterEnvelope.tsx
  lib/
    api.ts                   # 백엔드 fetch 래퍼
    animations.ts            # Framer Motion variants 모음 (캐치/먹기/셀레브레이션)
  types/
    emotion.ts                # backend/app/schemas/emotion.py와 1:1 대응하는 TS 타입
```

### Character.tsx 레이어 구조

`animationState` 하나(`idle | listening | eating | celebrating`)로 아래 3개 레이어가 각자 반응하도록 구성:

- **몸통**: 색상 3종 props로 스와핑, 스쿼시앤스트레치 담당
- **얼굴 (눈+입, 별도 레이어)**: 깜빡임, 씹기 모션
- **사지 (팔+다리, 별도 레이어)**: 캐치 동작, 셀레브레이션 회전

새 리액션이 추가돼도 이 3레이어 구조 안에서 확장하면 됨 — 레이어를 더 쪼개지 말 것 (관리 복잡도 증가).

### 상태 관리

Redux 등 불필요. 가볍게:
- `UserContext` (React Context 1개): `user_id`, `level`, `xp`, `onboarding_completed` — 로그인 후 세팅, 페이지 이동해도 유지
- 나머지(입력값, 애니메이션 진행 상태)는 각 컴포넌트 로컬 `useState`로 충분

### 데이터 흐름 (한 사이클)

```
InputFlow 제출 → lib/api.ts로 POST /emotion-logs 호출
→ 응답(편지+XP+퀘스트) 수신 → Character의 animationState를
  "listening" → "eating" → "celebrating" 순서로 전환하며 재생
→ 완료 후 UserContext의 level/xp 갱신 → 게이지바 자동 반영
```

### 타입 안정성

`types/emotion.ts`는 `backend/app/schemas/emotion.py`와 최대한 1:1로 맞출 것. 백엔드 스키마가 바뀌면 프론트도 타입에러로 바로 잡히도록. 파이썬 스키마 보고 TS 타입 만드는 작업을 요청받으면 필드명/옵셔널 여부까지 정확히 대응시킬 것.

### 레이아웃 정렬

- 대부분의 UI: **가운데 정렬** (동화적 세계관에 맞춤)
- **예외**: 편지 본문 텍스트는 **왼쪽 정렬** (실제 편지 읽는 느낌)

### 디자인 원칙 — "대담함은 한 곳에만"

**히어로 모먼트는 캐릭터가 먹이를 받아먹는 순간 하나뿐.** 반짝임/바운스/셀레브레이션 애니메이션은 이 순간에 집중하고, 그 외 UI(버튼, 카드, 네비)는 차분하고 절제되게 유지할 것. 다른 곳에 화려한 효과를 추가하고 싶은 충동은 참을 것 — 대담함을 여러 곳에 분산시키면 오히려 하나도 안 살아남음.

### 구조적 디테일 (세계관 반영, 최소 1개 이상 적용)

일반적인 UI 요소를 틈 아일랜드 세계관으로 치환:

| 일반적 요소 | 세계관 반영 버전 |
|---|---|
| 로딩 스피너 | 조각이 모여 편지가 접히는 모션 |
| 온보딩 진행 표시(1/4, 2/4) | 숫자 대신 조개껍데기/발자국이 채워지는 형태 |
| 카드 구분선 | 얇은 나뭇잎 모양 또는 점선(파도 느낌) |
| 섹션 라벨 | 아이콘이 이미 의미를 전달하므로 텍스트 라벨 최소화 |

### 마이크로카피(UI 문구) 톤 가이드

시스템이 아니라 **캐릭터/요정이 말하는 톤**으로 전부 통일. 버튼은 행동을 그대로 이름 붙일 것("제출하기" 대신 실제 행동어).

| 상황 | 쓰지 말 것 | 이렇게 쓸 것 |
|---|---|---|
| 로딩 중 | "Loading..." | "얼룩이가 듣고 있어..." |
| 편지함 비어있음 | "편지가 없습니다" | "아직 아무 말도 안 걸었네, 오늘 하루 얘기해볼까?" |
| API 에러 | "오류가 발생했습니다" | "얼룩이가 잠깐 딴 데를 봤나봐, 다시 한 번 눌러줄래?" |
| 입력 제출 버튼 | "제출하기" / "확인" | "먹여주기" |
| 안전화면(위기감지)만 예외 | - | 이 화면은 캐릭터 톤 배제, 명확하고 차분한 안내문 유지 (안전이 최우선) |

에러/빈화면 문구는 캐릭터 톤을 쓰되, 사과하지 않고 상황과 다음 행동을 명확히 전달할 것.

### 모바일 웹앱(PWA) 처리

이 서비스는 링크로 공유되는 웹앱이라 네이티브 앱이 아님 — 아래 처리 필수:

- **폰 프레임**: 데스크톱에서 열람 시 콘텐츠 최대너비 430px로 고정, 가운데 정렬, 바깥은 옅은 배경. 모바일에서는 자동으로 꽉 채워짐 (동일 코드로 양쪽 대응)
- `viewport` 메타태그에 `user-scalable=no` (핀치줌 방지)
- pull-to-refresh 기본 동작 방지
- `safe-area-inset` CSS로 노치/하단바 영역 회피
- PWA 매니페스트 설정 (`display: standalone`) — 홈화면 추가 시 주소창 없이 전체화면
- Open Graph 메타태그 설정 (링크 공유 시 로고+캐치프레이즈 미리보기 노출)

### 실사용 디테일 체크리스트

- 느린 네트워크 대비 이미지 최적화 (WebP, 압축)
- 연속 탭 방지: API 요청 중엔 버튼 비활성화 (중복 요청 차단)
- 텍스트 입력 시 키보드 올라와도 캐릭터/중요 UI 안 가려지게 레이아웃 처리
- 긴 편지 텍스트 오버플로우 대비 (스크롤 처리)
- 폰트(Gamja Flower, Jua) 프리로드 처리 — 늦게 로드되며 폰트 깜빡이는 현상(FOUT) 방지
- 접근성: 파스텔톤이라도 텍스트-배경 대비 WCAG 4.5:1 이상 유지, 특히 안전화면은 확실히 읽히게
- 터치 영역 최소 44×44px 확보

## 기본 원칙

1. **아트가 하나씩, 순서 없이 들어올 수 있음.** 채영님이 완성되는 대로 파일을 던져줄 예정이라, 어떤 순서로 와도 그때그때 맞는 컴포넌트에 바로 반영할 것.
2. **아트 없는 부분은 임시 플레이스홀더로 먼저 구현.** 실제 이미지가 없다고 개발을 멈추지 말고, 색깔 있는 도형(div)이나 이모지로 대체해서 레이아웃/로직/애니메이션을 먼저 완성해두고, 나중에 이미지 파일만 갈아끼우는 구조로 짤 것.
3. **매번 이미지 하나 받으면**: (1) 어떤 화면/컴포넌트에 쓰이는지 아래 매핑표에서 확인 → (2) 해당 컴포넌트에 반영 → (3) 임시 플레이스홀더였다면 실제 이미지로 교체 → (4) 간단히 확인 가능한 상태로 만들고 사용자에게 보고.

## 파일 수신 규칙

새 이미지 파일을 받으면 `frontend/public/assets/` 아래 적절한 하위 폴더에 저장:

```
frontend/public/assets/
  character/       # 펫 파츠 (몸통, 눈, 입, 팔, 다리) + 색상 3종
  fairy/           # 요정 전신 + 미니아이콘
  background/      # 섬, 하늘, 구름
  icons/           # 하단네비(홈/퀘스트/옷장), 편지봉투, 설정
  food/            # 감정 12개 먹이 아이콘
  branding/        # 로고, 스플래시
```

파일명이 애매하면 사용자에게 "이거 어디에 쓰는 이미지야?"라고 물어보고 진행할 것 — 짐작으로 잘못된 폴더/용도에 넣지 말 것.

## 화면 구현 우선순위

아트가 부분적으로만 들어와도, 완성된 부분부터 순서대로 진행:

1. **홈 화면** (`app/page.tsx` 또는 `app/home/page.tsx`) — 제일 먼저. 캐릭터+배경+레벨게이지+입력버튼+하단네비
2. **입력 플로우** (자유텍스트 / 구조화입력 2경로) — 아트 의존도 낮음, 먼저 만들어도 됨
3. **요정 연출 + 캐릭터 먹기 애니메이션** — `PROJECT_SUMMARY.md`의 "13. 애니메이션 참고" 섹션 그대로 Framer Motion으로 이식
4. **편지함 / 퀘스트 / 옷장 화면**
5. **온보딩** (로그인 → 닉네임 → 펫+요정 등장 → 먹이튜토리얼 → 이름짓기) — 제일 마지막, 다른 화면 컴포넌트 재사용해서 조립

## 백엔드 연동 규칙

- API 베이스 URL은 `.env.local`의 `NEXT_PUBLIC_API_URL`로 관리 (로컬은 `http://localhost:8000`)
- `POST /emotion-logs` 호출 시 스키마는 `backend/app/schemas/emotion.py` 참고 — `user_id` 필수
- 응답의 `today_quests`는 배열(2~3개), `food_icon`은 감정명 문자열 → 프론트에서 아이콘 매핑 필요
- 위기신호(`emotion: "무기력"`이면서 `id: "crisis"`인 특수 응답)는 일반 편지 UI가 아니라 **별도의 차분한 안전 화면**으로 분기 처리할 것 (일반 캐릭터 리액션 연출 생략)

## 애니메이션 구현 시 참고

`PROJECT_SUMMARY.md`의 "13. 애니메이션 참고" 섹션에 캐치→먹기→셀레브레이션 시퀀스가 offset 기반으로 상세히 정리되어 있음. HTML `element.animate()` keyframe 구조를 그대로 Framer Motion의 `animate` prop / `useAnimate` 훅으로 옮기면 됨. 스쿼시앤스트레치 + 레이어 분리(몸통/눈/입/팔) + 바운스 이징을 반드시 유지할 것 — 그림 퀄리티보다 이 타이밍감이 "살아있는 느낌"의 핵심.
